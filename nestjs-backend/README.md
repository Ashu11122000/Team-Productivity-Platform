# Team Productivity Platform — NestJS Backend

Enterprise-grade NestJS backend for the **Team Productivity Platform**, responsible for productivity management, analytics, notifications, reminders, and collaboration features.

This backend is designed using **Clean Architecture**, **SOLID principles**, and enterprise development practices to provide a scalable, maintainable, and production-ready API.

Unlike traditional monolithic applications, authentication is intentionally separated into a dedicated FastAPI service. NestJS focuses exclusively on productivity domain responsibilities while securely validating JWT tokens issued by the authentication service.

---

The Team Productivity Platform is a distributed application composed of multiple services that work together to deliver a modern productivity experience.

# Architecture

The NestJS backend follows a microservice-inspired architecture where business domains are isolated into independent modules.

Each module follows the same enterprise implementation pattern.

```
Controller
      │
      ▼
Service
      │
      ▼
Repository
      │
      ▼
TypeORM
      │
      ▼
PostgreSQL
```

Entity-to-response transformations are delegated to dedicated Mapper classes to prevent leaking persistence models outside the application layer.

# Authentication Architecture

Authentication ownership belongs entirely to the FastAPI backend.

NestJS intentionally does **not** perform authentication-related operations.

NestJS never:

- Registers users
- Authenticates users
- Generates JWT tokens
- Stores passwords
- Refreshes tokens

NestJS only validates incoming JWTs before allowing access to protected resources.

Authentication flow:

```
User
   │
   ▼
FastAPI Login
   │
   ▼
JWT Token
   │
   ▼
Frontend
   │
   ▼
NestJS Request
   │
   ▼
JwtAuthGuard
   │
   ▼
JwtStrategy
   │
   ▼
Authenticated Request
```

---

# JWT Contract

NestJS validates JWT tokens generated by FastAPI.

Validation includes:

- Signature verification
- Issuer validation
- Audience validation
- Token expiration
- JWT payload integrity

Only validated requests are allowed to access protected APIs.

# Clean Architecture Pattern

Each business module follows the same implementation pattern.

```
Controller

↓

Service

↓

Repository

↓

Mapper

↓

DTO

↓

TypeORM

↓

PostgreSQL
```

Responsibilities are clearly separated.

| Layer      | Responsibility                 |
| ---------- | ------------------------------ |
| Controller | HTTP handling                  |
| Service    | Business rules                 |
| Repository | Database access                |
| Mapper     | Entity ↔ DTO conversion        |
| DTO        | Request and response contracts |
| Entity     | Persistence model              |

Business logic never resides in controllers or repositories.
